The procedure below has not been exercised in production. Historical receipts establish their recorded observations only; current live state is unknown.

## Local reliability extensions

The November 21 local implementation adds the optional reviewed `supabase/functions/news-agent/sql/notification-incidents.sql` contract before deploying notifier wiring for `news-agent`/`news-collect`. It uses a private RLS incident ledger behind service-role-only RPCs and retains existing fixed-recipient Gmail configuration; it introduces no new environment variables. SQL defaults are a 24-hour reminder interval, a 15-minute failed/uncertain delivery backoff and a one-minute fenced claim lease, with a ten-second total optional persistence/SMTP deadline. The ledger admits at most 10,000 records and prunes only recovered records older than 90 days without a live claim. SMTP acceptance is a delivery acknowledgment, not exactly-once delivery; timeouts remain uncertain and cannot trigger immediate blind replay. Processing continues when notification delivery fails. Recovery requires explicit successful observation of the same entity/configuration, never absence from a narrow invocation. This local change is not evidence that the SQL or notifier bundle is installed live.

The companion `supabase/functions/news-agent/sql/source-health.sql` extension follows checkpoint migration `20261115204734` and precedes the updated collector bundle. Its owner-managed trusted roster starts empty: populate exact `source_key`/`config_hash` pairs from the reviewed deployed configuration using `configurationHash`, not historical checkpoint rows or invocation selections. It records head checks, accepted work, semantic progress and typed coverage reasons separately from `last_success_at`/`covered_through`, and matches configuration generations to exclude stale observations. The finish RPC retains eight-argument compatibility through defaulted additions; operations reports `rosterConfigured=false` when the trusted roster is empty or unavailable, rather than fabricating coverage. A partially progressing archive can still need source-head freshness attention; finite upstream history gaps are not transport outages. Install and review compatible operations/dashboard definitions against the exact existing schema before deployment; reference installers are not blanket replay instructions.

For an **existing operations/alerts installation**, do not replay `operations.sql` or `agent-alerts.sql`: their CREATE installers are not forward migrations. Generate the reviewable forward artifact locally with:

```sh
node tools/prepare-reliability-upgrade.mjs > /tmp/warpcore-reliability-upgrade.sql
```

The generator reads canonical function definitions and the health-progress block rather than copying their logic. Review the output against the inventoried schema before any separately authorized application. It requires the full existing operations/alerts stack and separately installed source-health extension, failing closed on missing prerequisites. In one transaction it installs the private semantic-progress ledger/triggers, replaces health/run-progress/alert-refresh functions with `CREATE OR REPLACE`, extends the alert-code check, and updates the dashboard projection only when already installed. It retains existing function identities, owners and grants, durable queue/evidence/financial/incident rows and enable flags. It performs no deployment, database connection or activation when generated. New progress timestamps come from observed lifecycle events; existing unknown creation/progress times are not backfilled as current activity.

## Unpaid verification source recovery (November 23)

The prepared extension `20261123051515_unpaid_verification_source_recovery.sql` (matching source installer: `supabase/functions/news-agent/sql/unpaid-verification-recovery.sql`) reopens only deferred, unpaid source acquisition for `source_timeout`, `source_transport_failure` or `source_http_failure`. It permits at most **three retries per job**, each after **15 minutes** from both the observed failure and any prior retry, and only when the job's recorded creation is within **24 hours**. Unknown creation/failure clocks do not qualify. Producer and verification gates must be enabled; existing pending verification and downstream publication work take precedence. Recovery preserves `submit_enabled` and normal preview semantics; it does not authorize posting. HTTP failures, parser failures and response-body limits retain distinct sanitized diagnostics; parser/body-limit failures are not retry-eligible.

Eligibility is rechecked under the verification/admission locks and child-run lock. Any paid attempt, verification audit, receipt, inbox/publication record for the story, blocked run, nonzero spent/held amount or active lease excludes recovery. Each reopening retains immutable private before-state/revision evidence in `shadow_agent.verification_source_retry_audit`; it does not reset accounting or erase the failed observation. Unknown paid-provider outcomes and their holds remain for reconciliation, with no paid replay or financial release. Recent acquisition failures remain degraded health observations; editorial skips and unpublishable drafts are classified separately and do not establish a publisher outage.

Install only after the existing verification-job/outcome-reason contracts and reliability health clocks; choose the migration or matching source installer once, not both. The extension checks installed selector shapes and preserves their unrelated gates. For an existing operations/alerts stack, generate and review the health upgrade above **after this extension**, then deploy the matching worker/schema changes through the reviewed stop/resume boundary; never replay the original CREATE installers. V8 schema/prompt budgets partition summary and significance around actual attribution/link costs, as best-effort generation guidance: providers may strip schema keywords. Trusted final 300-grapheme/3000-byte publication validation remains authoritative, and overlong drafts are rejected without truncation. This section describes prepared code and installation order, not a deployment receipt.

## Stop controls and in-flight boundaries

Choose the required boundary and record its prior state before making any authorized operational change. Read back each control afterward.

| Boundary | Controls | Work that can remain in flight |
|---|---|---|
| New recurring and immediate pipeline dispatch | Pause the exact pipeline cron job and set `shadow_agent.producer_settings.enabled=false`; inspect any older jobs and explicit legacy environment gate | Already queued pg_net HTTP and running function invocations are not cancelled. Current `pipeline_enqueue` shares the producer gate, so pausing cron alone leaves event dispatch possible |
| New verification and handoff | `shadow_agent.verification_settings.enabled=false` and `submit_enabled=false`; account separately for backfill | Claimed model calls, committed decisions, verified receipts and already admitted inbox rows can survive the change |
| New public sends | Reviewed deployed publisher enable lock (`WARPCORE_PUBLISH_ENABLED`) and its dispatch controls | Existing sends may already have logged in or written remotely. Disabled handler requests do not provide a reconciliation service; use a separate reviewed read-only reconciliation path while sending is disabled |
| New legacy producer submissions | Keep `shadow_agent.spending_policy.exclusive_agent=true` while the agent is the intended producer; verify legacy task retirement independently | Existing legacy inbox/publication work remains durable. The exclusivity fence does not stop legacy reasoning or its costs |

Do not disable collection merely to stop editorial decisions if independent safe collection is intended; the shared pipeline gate suppresses scheduled dispatch, so retaining collection requires an explicitly reviewed existing collector invocation path. Do not start a second producer or recreate historical jobs to obtain it. Stop controls do not retract published records or reverse financial dispatch.

## State-preserving rollback and recovery

1. Capture the inventory and stop at the required boundary. Allow or inspect already dispatched work; wait for durable outcomes/lease expiry rather than treating a flag change as cancellation. Preserve exact artifact manifests and compatibility requirements before selecting a previous reviewed bundle.
2. Retain collection queues, captured evidence, checkpoints, assessments, receipts, inbox rows, immutable publication payloads/keys, run revisions, leases, reservations, settlements, audits and uncertain holds. Do not run a fresh-start backlog reset as incident recovery. Never delete evidence, reset financial rows or release unknown holds to make work appear healthy.
3. Reconcile every sending/uncertain publication using its original account DID, collection and record key. Ordinary posts use `app.bsky.feed.post`; native reposts use `app.bsky.feed.repost` and require the exact stored subject URI/CID/author. Read the exact authoritative remote record and compare payload/identity. A missing read, timeout or mismatch is unresolved, not permission for a blind retry, new TID or duplicate post. Preserve remote URI/CID and durable receipts. Never restore a post-only publisher while repost work remains unresolved.
4. Reconcile model dispatch independently from publication. Known usage settles even for rejected content; unknown usage retains its hold. Only already reviewed narrow workflow quarantine controls may release workflow fences for their exact eligible errors; they do not release money or replay failed requests. Generic uncertain outcomes require explicit operator reconciliation. Preserve revisions and audit identities across any compatible artifact rollback; do not down-migrate durable state or weaken grants to run old code.
5. Validate installed schema/RPC compatibility and collection-aware readback before restoring an artifact. Keep verification/submission off while validating new observations and retained queues. Restore only the intended single producer. Switching to a legacy producer requires agent handoff disabled and the existing shared admission/exclusivity boundary; do not clear exclusivity while both producers can submit.
6. Read back gates, exact jobs and roster, then resume stages deliberately and observe source freshness, semantic progress, guarded handoffs, publication readback and financial holds. Quiet review or draft rejection may be healthy; neither establishes publisher failure. Missing observations never establish recovery. Record outstanding uncertainties and the exact evidence for each recovered entity.
